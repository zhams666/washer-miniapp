# 小程序全功能回归测试计划

> 本文用于验证当前已实现的用户端小程序、商户端小程序、PC 管理后台和后端接口。测试应使用本地环境和可恢复的测试数据，避免影响生产数据。

## 目标与范围

**目标：** 确认现有功能可以完成完整闭环，核心链路中的用户、金额、订单、设备和权限数据保持一致。

**涉及系统：**

- 微信小程序：用户端和商户端分包页面。
- 后端：Spring Boot + MySQL，本地默认地址为 `http://127.0.0.1:18080`。
- PC 管理后台：Vue + Vite，本地默认地址为 `http://127.0.0.1:18073`。
- 微信开发者工具：用于编译、清缓存和模拟小程序交互。

**执行原则：**

- 每个模块完成后记录结果、测试账号、订单号、门店/设备编号和异常截图。
- 涉及金额、设备启停、删除操作的测试，优先使用专用测试账号、测试门店和测试设备。
- 每次修改小程序的 `app.json`、分包配置、自定义导航栏或页面逻辑后，必须在微信开发者工具中执行“清除缓存/数据”并重新“编译”。
- 本地环境已关闭真实微信支付时，只验证订单创建、支付模拟结果和金额流水，不验证真实支付回调。

## 测试数据准备

开始前在本地数据库或 PC 后台准备下列数据；名称可按实际环境替换，但需记录真实编号。

| 数据 | 建议状态 | 用途 |
| --- | --- | --- |
| 用户 A | 有足够余额、允许登录 | 钱包洗车、卡券、资料修改 |
| 用户 B | 余额为 0 或不足 | 余额不足、充值、排队 |
| 门店 1 | 至少一台空闲设备 | 立即洗车、设备状态验证 |
| 门店 2 | 设备全部忙碌 | 排队流程验证 |
| 设备 D1 | 初始为空闲 | 启动、完成、取消洗车 |
| 门店 1 的充值套餐 | 上架且可购买 | 门店充值验证 |
| 洗车卡套餐 | 上架且可购买 | 卡券购买、扣次验证 |

建议建立一份测试记录，至少包含：测试时间、执行人、模块、步骤编号、结果、关联 ID、截图路径、缺陷编号。

## 任务 1：本地环境与基线确认

### 1.1 启动后端

在项目根目录 `E:\workspace\自助洗车\washer-main` 执行：

```powershell
$env:WASHER_DB_PASSWORD = '<本地 MySQL 密码>'
$env:WECHAT_MINIAPP_MOCK_LOGIN_ENABLED = 'true'
mvn -f .\backend\pom.xml spring-boot:run
```

如果当前目录已经是 `E:\workspace\自助洗车\washer-main\backend`，改为执行：

```powershell
mvn spring-boot:run
```

验证步骤：

1. 日志出现应用启动完成，且没有端口占用、数据库连接失败或迁移失败。
2. 在另一终端执行 `curl.exe http://127.0.0.1:18080/api/ping`。
3. 确认接口返回正常响应。

预期结果：后端可访问；若 18080 已被旧 Java 进程占用，应先确认该进程用途后终止旧进程，再重新启动。

### 1.2 启动 PC 管理后台

在项目根目录执行：

```powershell
cd .\admin-web
npm run dev:local
```

验证步骤：

1. 浏览器打开 `http://127.0.0.1:18073`。
2. 登录页和后台首页可正常加载。
3. 浏览器开发者工具中无接口跨域错误，接口请求指向 `http://127.0.0.1:18080`。

预期结果：PC 管理端能够登录和访问菜单，前后端地址均为本地地址。

### 1.3 编译小程序并确认导航栏

验证步骤：

1. 在微信开发者工具中打开项目根目录。
2. 点击“清除缓存”，选择清除数据和编译缓存。
3. 点击“编译”。
4. 依次点击底部“首页、门店、榜单、订单、我的”。

预期结果：每次点击后，页面内容、当前路由和底部高亮项一致；不会停留在上一页、卡住或无法点击其他入口。

### 1.4 记录测试基线

记录用户 A、用户 B 的余额、洗车卡次数、积分；记录门店 1、门店 2、设备 D1 的初始状态和待测套餐价格。

预期结果：后续所有金额、订单和设备状态变化都能与该基线比较。

## 任务 2：导航、登录与个人资料

### 2.1 底部导航栏

操作路径：`首页 -> 门店 -> 榜单 -> 订单 -> 我的 -> 首页`。

验证项：

1. 每页展示对应页面内容，没有旧页面残留。
2. 当前标签图标和文字高亮正确。
3. 连续快速切换标签后仍可操作。
4. 从“我的”进入管理端后返回，底部导航栏仍与用户端页面一致。

### 2.2 未登录状态

验证步骤：

1. 在开发者工具中清除本地存储。
2. 重新编译并打开“我的”。
3. 点击需登录入口，例如洗车订单、消费明细、卡券、个人资料。

预期结果：显示未登录状态和合理的登录引导；受保护页面不能以空用户身份进入；页面不会无限加载。

### 2.3 手机号登录与账号切换

验证步骤：

1. 以用户 A 完成手机号登录或本地模拟登录。
2. 检查首页、我的、钱包、订单中的姓名、余额和历史数据是否刷新为用户 A 数据。
3. 退出或切换为用户 B。
4. 重复检查上述页面。

预期结果：两个账号数据隔离；用户 B 不会看到用户 A 的余额、订单、卡券或个人资料。

### 2.4 修改个人资料

验证步骤：

1. 用户 A 进入“修改信息”。
2. 修改昵称和头像，保存后返回“我的”。
3. 重新进入资料页并重启/重新编译小程序。
4. 在 PC 管理后台用户详情中核对资料。

预期结果：资料保存后持续生效，用户端和 PC 后台显示一致。

### 2.5 授权拒绝与登录失败

验证步骤：拒绝手机号授权或模拟登录接口失败后，继续尝试进入需要登录的页面。

预期结果：有明确提示，仍可返回或重新尝试；没有白屏、卡死、重复弹窗或无休止加载。

## 任务 3：首页、门店、定位与扫码

### 3.1 首页定位与降级显示

验证步骤：

1. 允许定位授权，检查首页推荐门店、距离和服务入口。
2. 拒绝定位授权，重新进入首页。

预期结果：允许定位时按位置展示；拒绝定位时仍可浏览门店并显示可理解的默认内容，不阻塞其他操作。

### 3.2 首页快捷入口

依次测试：`团购核销`、`扫码洗车`、`门店充值`、`通用充值`、`加盟联系`、`洗车教程`。

预期结果：

1. 每个入口跳转到正确页面或显示正确操作提示。
2. 加盟联系信息与 PC 后台配置一致。
3. 教程、说明类页面能正常返回首页。

### 3.3 门店列表与设备状态

验证步骤：

1. 打开门店列表，核对门店状态、距离、空闲设备数量和营业状态。
2. 在 PC 后台分别将设备 D1 设置为空闲、使用中、禁用。
3. 刷新小程序门店列表和门店详情。

预期结果：小程序的可用状态和可选设备与 PC 后台设置一致；禁用设备不可发起洗车。

### 3.4 门店详情与设备选择

在门店 1 依次选择空闲、使用中、禁用的设备并尝试发起洗车。

预期结果：只有空闲设备可正常进入洗车流程；繁忙设备给出提示或进入排队；禁用设备不可选择。

### 3.5 扫码洗车

验证步骤：

1. 分别使用有效的门店码、设备码或二维码参数进入扫码洗车。
2. 使用无效、过期或不存在的二维码参数测试。

预期结果：有效二维码定位到正确门店/设备；无效二维码显示可理解的错误，不创建订单、不改变设备状态。

## 任务 4：充值、钱包、支付与排队

### 4.1 余额不足引导

验证步骤：

1. 使用用户 B 选择门店 1 的可用设备并尝试钱包洗车。
2. 确认余额不足后进入充值入口。
3. 返回洗车页或完成充值后继续操作。

预期结果：余额不足提示正确；用户已选门店、设备等上下文不丢失或有明确返回路径。

### 4.2 门店充值与通用充值

验证步骤：

1. 选择门店 1 的上架充值套餐创建充值订单。
2. 在关闭真实微信支付的本地环境中，完成项目提供的模拟支付流程或验证支付待处理状态。
3. 进入钱包/消费明细查看余额与流水。
4. 在 PC 后台的支付订单、钱包流水和用户详情中核对。

预期结果：每次操作只产生一条正确的充值订单和流水；金额、用户、门店、订单状态三端一致。

### 4.3 钱包流水

验证步骤：分别完成一次充值、一次洗车扣款、一次退款或取消（如支持），查看用户端和 PC 后台流水。

预期结果：流水方向、金额、时间、关联订单和余额变化一致；不存在重复扣款或重复入账。

### 4.4 排队

验证步骤：

1. 选择门店 2 的繁忙设备，在允许排队距离内加入排队。
2. 检查排队状态、队列位置和关联门店/设备。
3. 在超出允许距离的模拟位置尝试排队，或修改定位后重新校验。
4. 取消排队或让前序订单结束后观察状态变化。

预期结果：同一用户不会生成重复排队记录；距离不符合要求时无法排队；取消和自动顺位后的状态正确。

## 任务 5：洗车、订单与设备状态

### 5.1 钱包洗车启动

验证步骤：

1. 用户 A 在门店 1 选择空闲设备 D1，使用钱包发起洗车。
2. 立即刷新洗车页、订单页、门店详情和 PC 后台设备页。

预期结果：

1. 仅生成一笔进行中的洗车订单。
2. D1 状态变为使用中/运行中。
3. 用户余额按规则扣减并有对应流水。
4. PC 后台订单、设备状态与小程序一致。

### 5.2 重复提交保护

在发起洗车按钮上快速连续点击，或在网络延迟后重复提交。

预期结果：不产生重复订单、重复扣费或重复设备启动；界面有提交中或防重复提示。

### 5.3 完成洗车

验证步骤：通过正常完成入口、设备状态更新或后台允许的测试操作结束该次洗车。

预期结果：订单仅完成一次；D1 恢复空闲；订单详情、设备日志、钱包流水和 PC 后台数据一致。

### 5.4 进行中与已完成订单

验证步骤：分别查看进行中订单和已完成订单，进入订单详情并尝试可用操作。

预期结果：列表分类、状态文字、金额、门店、设备、时间和详情一致；不允许对已完成订单重复完成或取消。

### 5.5 取消与异常停止

在项目支持的状态下取消订单或模拟设备异常停止。

预期结果：设备、订单、余额和退款流水按业务规则同步；同一订单不会同时显示为进行中和已取消/已完成。

## 任务 6：卡券、会员、榜单、积分与内容入口

### 6.1 洗车卡购买与扣次

验证步骤：

1. 使用用户 A 购买一张上架洗车卡（使用本地模拟支付或已有测试卡）。
2. 在“我的卡券”检查卡状态、有效期、剩余次数。
3. 使用该卡完成一次洗车并再次检查剩余次数。

预期结果：购买、订单、卡券记录和剩余次数一致；一次洗车只扣一次。

### 6.2 卡券异常状态

验证已过期、次数用尽、禁用或不适用门店的卡券（按当前系统可配置状态）。

预期结果：不可用原因明确；系统不会扣减无效卡券或允许越权使用。

### 6.3 会员信息

验证步骤：检查“我的”中的会员等级、到期时间和权益；在 PC 后台调整会员有效期/状态后刷新小程序。

预期结果：前后端会员状态一致，过期或变更后显示正确。

### 6.4 榜单

验证步骤：切换榜单提供的范围或维度，例如全国、城市、门店等。

预期结果：列表可加载、排序稳定、空数据有正常占位；切换范围不会让底部导航高亮错位。

### 6.5 优惠券、积分、邀请和内容页面

验证步骤：打开优惠券、积分商城、邀请、教程和帮助类入口。

预期结果：已实现的展示、跳转和返回能力正常。若积分兑换、邀请奖励等后端业务尚未实现，仅记录为“入口可用，业务待实现”，不将其误判为回归故障。

## 任务 7：小程序商户端与权限

### 7.1 各角色登录

使用平台管理员、加盟商、门店管理员、员工四种测试账号分别进入管理端。

预期结果：每种角色可看到与其权限匹配的菜单和数据范围；无权限入口不可访问或有明确拒绝提示。

### 7.2 数据范围隔离

分别检查各角色可见的经营指标、门店、设备、订单、财务和用户数据。

预期结果：加盟商仅能看到授权加盟范围；门店管理员和员工不能读取其他门店数据；普通用户不能直接进入商户受保护页面。

### 7.3 设备操作权限

验证有权限角色对设备的查看、启停或状态调整；再用无权限角色重复请求或尝试进入同一页面。

预期结果：授权角色操作后状态同步；未授权角色无法执行，后端同样拒绝请求，不能仅依赖前端隐藏按钮。

### 7.4 用户资产操作与审计

在专用测试用户 A 上验证后台可用的余额调整、罚款/扣款、洗车卡调整功能。

预期结果：每次调整有操作人、原因、时间和金额/次数记录；用户端余额、卡券和流水同步；不得误操作非测试用户。

### 7.5 管理端返回用户端与会话处理

验证步骤：从“我的”进入管理端，再返回用户端；退出管理端或清除令牌后尝试直接进入商户受保护页面。

预期结果：页面跳转稳定；商户令牌失效后会被引导登录，不会保留旧账号的权限或数据。

## 任务 8：PC 管理后台

### 8.1 路由与菜单

逐一访问实际启用的后台菜单：仪表盘、运营活动、门店、设备、用户、订单、钱包/支付、卡券、会员、结算、加盟联系、权限管理等。

预期结果：菜单可进入、刷新不白屏、无死循环加载；无权限菜单按角色正确隐藏或拦截。

### 8.2 门店与设备管理

验证步骤：创建或编辑专用测试门店/设备，调整启用状态、设备状态和基础信息，然后刷新小程序核对。

预期结果：保存后数据一致；禁用影响用户端可操作性；测试结束后删除或恢复本次新增的临时数据，避免污染环境。

### 8.3 用户、订单与支付追溯

使用任务 4、任务 5 产生的订单号，在后台查询用户、洗车订单、充值订单、支付状态和钱包流水。

预期结果：可通过订单或用户追溯关联记录；金额、状态和时间一致；不存在孤立订单或无对应流水的扣款。

### 8.4 加盟联系与权限配置

验证步骤：在后台修改测试用加盟联系信息或角色权限，重新登录小程序商户端后检查展示与访问范围。

预期结果：修改只对有权限的目标生效；权限调整后旧会话按系统规则刷新或失效，不发生越权。

### 8.5 仪表盘与结算数据

对照本轮测试产生的订单、充值和设备状态，查看仪表盘汇总和结算数据。

预期结果：统计口径与订单、钱包流水一致；若存在异步统计延迟，应记录延迟时间和最终一致性结果。

## 任务 9：异常回归、生产边界与验收

### 9.1 后端不可用与恢复

验证步骤：在测试环境暂停后端或临时断开网络，访问首页、订单、支付和管理端页面；随后恢复后端。

预期结果：前端显示可理解的失败/重试状态，不假装成功；恢复后可重新加载，不需要重装小程序。

### 9.2 开发者工具缓存回归

验证步骤：执行一次“清除缓存/数据 -> 编译 -> 切换五个底部标签 -> 进入/返回管理端”。

预期结果：页面和导航栏状态一致；不存在首次打开正常、重新编译后卡住的情况。

### 9.3 生产环境暂不纳入本地验收的事项

以下需要独立的生产/预发布配置和真实外部依赖，不应以本地模拟结果替代：

- 微信真实支付签名、下单、回调和退款。
- 真实设备控制协议、设备网络和设备回执。
- 手机号真实授权与微信身份识别。
- 真实二维码、GPS 定位精度、业务域名和隐私合规配置。

### 9.4 缺陷记录与发布门槛

每个问题需记录复现步骤、账号、门店/设备编号、订单号、接口响应、日志时间和截图。

下列问题属于发布阻塞项：

1. 登录身份或数据隔离失效。
2. 充值、扣款、退款、订单金额不一致或重复记账。
3. 设备状态与洗车订单状态不一致，或重复启动设备。
4. 任意角色可以访问超出权限范围的数据或操作。
5. 底部导航栏与实际页面不一致、页面卡住或主要入口无法跳转。

## 测试完成标准

全部模块均执行并有记录；核心链路“登录 -> 充值/余额 -> 发起洗车 -> 订单完成 -> 钱包流水 -> PC 后台追溯”至少成功完成一次；所有发布阻塞问题已修复并完成复测，或获得明确的延期处理结论。
